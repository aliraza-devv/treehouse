## Type and scroll feel
- Fonts: Fraunces variable (headings, opsz 144, weight 800, SOFT 55, WONK 1, set in globals.css; closest free match to the owner's Briston and Clara references; Briston is a paid font), Figtree (body and UI), Caveat (Section 3 margin notes). Hero and Section 2 headings are set big (up to about 9rem) with one warm word. Hero and climb copy share one structure in `src/components/ui/stageType.js` (same left edge, bottom edge, heading and subline sizes; every climb stage is a two line heading plus a subline). The two photographic backdrops live in `src/components/ui/journey/backdrops.jsx` (graded stock, credited in public/images/journey/CREDITS.txt). Climb copy never fades: lines rise out of masks (ScrollOverlay.jsx), so the type is always full colour. Loader: `src/components/ui/Preloader.jsx` covers the page from the first paint and draws the hero's own treehouse (`loaderArt.js`) on a fixed CSS clock (about 0.8s: `SPEED` in loaderArt.js scales the whole drawing, nothing runs per frame in script); when fonts, the scroll runway and the 3D scene are all in (reported through `src/lib/loadState.js`; Scene.jsx and CanvasBoundary.jsx mark the scene) the window, lantern and string lights come on, "Come on up." appears and the canopy lifts away on compositor animations (about 1s). The hero intro starts 170ms into the lift (`onSiteReady`). Load speed, in order of what it was waiting on: the 3.7 MB child model (`public/models/child/child.glb`, 3.3 MB of it PNG textures) gates the 3D hero, so it is preloaded from `layout.js` (react-dom `preload`, inside the component, same URL and credentials as three's loader so the browser reuses it: one request, checked) and the scene and scroll-runtime chunks start downloading when their wrapper files evaluate (`SceneLoader.jsx`, `ScrollDriver.jsx`, behind the shared `src/lib/hasWebGL.js` probe) instead of after hydration; the walkway photos are `fetchPriority="low"` so they no longer queue ahead of those; the 3D scene's own fade-in is 450ms, not 1.4s, since the loader covers it. If it must get faster still, the next lever is the child model's textures (resize or KTX2), which changes quality, so it was left alone. SECOND PASS (measured in real Chrome on the owner's laptop class, Intel UHD 630, 12 threads, production build; the numbers below were 7.8s for the 3D scene and 9.7s for the hero before): (1) the 3D scene was waiting on its 65 shader programs ONE AT A TIME (three.js blocks on each as it is created; about 5s of the 7.8s), so `Precompile.jsx` hands them all to the driver at once (`compileAsync`, with a small render target bound so the programs match the post stack's real ones; it also walks the composer's passes for their ShaderMaterials) and the render loop (`frameloop` in Scene.jsx) only starts when they are done: the compile takes about 0.5s and no longer freezes the page; the fade-in gate is 4 frames, the scene's own fade is 1s because it can now arrive after the loader has gone; (2) the loader no longer waits for the scene past `SCENE_CAP_MS` (2200ms from the start of loading): past it, once fonts and the runway are in, it leaves, the hero arrives over the forest colour and the scene fades in when ready (on a quick machine the scene is ready first and nothing is cut); (3) the drawing's minimum time is read off the wall clock from first paint, NOT off the CSS animation's clock, which goes stale while the scene boots and had held the loader up about 2.5s after everything was ready; (4) the loader's exit and the hero's intro are Web Animations with their delays inside them (compositor), not GSAP or timers, so a busy main thread cannot hold them back (`markSiteReady(delayMs)` signals at the start of the exit and tells the hero how long to wait). Result on that laptop: scene ready about 4.5s (was 7.8s), loader leaves at about 2.2 to 2.5s, hero words begin about 3s (was 9.7s) and settle by about 3.8s. What is still slow, and why: the browser parsing and running the 3D scene's code (about 1.1s block), page-wide GSAP setup in the Journey sections at hydration (about 0.5s) and the runtime painting of textures (about 1s) all share the one main thread, so a CPU 4x slower than that laptop still takes about 8s to the hero. The next levers if needed: start the below-the-fold sections' GSAP setup only after the hero has arrived, paint textures in a worker (OffscreenCanvas), and shrink what the scene chunk imports. How to measure again: build, `next start -p 3100`, and drive Chrome with puppeteer-core (install it OUTSIDE the project) recording `__treehouseLoad.parts`, the loader's `data-lit`, and the hero heading's opacity; headless first paint is about 1.1s on its own (GPU start), so judge the loader from `loaderLit` and the hero, not FCP. Hard stop 6s, CSS failsafe 9s, reduced motion fades instead of lifting.
- Scroll: Lenis in lerp mode (`src/lib/lenis.js`, lerp 0.09, smooth anchors), driven by the gsap ticker; the scroll driver adds only a short damper (`SMOOTH_TAU` 0.12) and GSAP scrubs use `scrub: true`, so smoothing is not stacked. The 3D scene steps its quality tier down when it cannot hold about 45 fps (`QualityGovernor` in `Scene.jsx`, tiers in `PostProcessing.jsx`).
